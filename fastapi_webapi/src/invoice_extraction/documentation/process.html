Invoice Extraction — Engineering Reference

Existing process: email ingestion, extraction and routing

Documents the pipeline as implemented today — stage by stage, with the gating thresholds and routing rules currently in force. Written for engineers maintaining or extending invoice_extraction; module/function names are used directly.

Module: invoice_extraction Entry point: email_pipeline.py Rules: decisions.py
01 — Overview

Three stages, one orchestrator

email_pipeline.EmailPipeline.run() is the entry point for one email. It composes two independently runnable pipelines — ingestion_pipeline and extraction_pipeline — then applies pure routing logic (decisions.decide_email) and persists the outcome. Every stage is wrapped in an MLflow span (see §08), so a single trace answers "what happened to this email, and why".

Design intent Ingestion and extraction stay decoupled on purpose: ingestion classifies and extracts nothing, extraction never sees the whole email — only one already-split PDF. The orchestrator is what restores the per-email view, so ingestion/extraction can still be run and tested independently of routing.
Where things live Prompts per stage: prompts/. One LLM call per stage: nodes/. Tunable constants (paths, limits, confidence threshold): config.py. Pydantic schemas: models/.

03 — Ingestion

LOAD → SEGMENT → SPLIT → PERSIST

Classifies and extracts nothing. The only judgement call is where one document ends and the next begins inside a multi-document attachment — and even that is checked deterministically before being trusted.

LOAD

Fetch from Outlook

invoice_utils.outlook_loader.fetch_inbox_emails

Messages are pulled live via Microsoft Graph (app or delegated auth) into sender, subject, body, reception date, message_id, thread_id and raw attachments — including zip expansion, bounded by MAX_ZIP_* in config.py. The standalone .msg file loader has been removed; Graph is the only ingestion source now. skip_message_ids lets the loader skip downloading attachments for messages already in the database (see §02).

SEGMENT

Document boundary detection

nodes.segment_document · span 1-chunking

An LLM call reads the whole attachment PDF (base64) and proposes page-range boundaries for each accounting document it contains — one attachment can hold several invoices back to back.

  • Page count is never asked of the model — it is computed deterministically (invoice_utils.pdf_splitter.count_pages), since VLMs cannot count pages reliably.
  • Malformed PDFs (broken xref tables) are repaired up front via ensure_readable() so the page count, the model and the splitter all see the same bytes.
Validation invoice_utils.pdf_splitter.validate_segmentation(documents, total_pages) checks the model's proposed boundaries against the real page count. A gap loses a document; an overlap duplicates one — both are logged as coverage problems and surfaced in EmailIngestionResult.problems, but do not block ingestion.
SPLIT

Cut into single-document PDFs

invoice_utils.pdf_splitter.split_pdf

One PDF written per detected document boundary. Non-PDF attachments are stored as-is (counted as annexes, not segmented).

PERSIST

Write the manifest

IngestionPipeline.ingest_email

Writes docs/processed_emails/<YYYYMMDD-HHMMSS>_<sanitized subject>/email_content.json (sender, subject, body, reception date, message_id, thread_id, annex/PDF counts) plus every split PDF. The timestamp is the email's own reception date, not now(), so reprocessing one email always produces the same name; it also sorts the output directory chronologically and separates the same-subject emails that collide routinely. IngestionPipeline.run() always ingests — there is no manifest/skip check at this layer any more. Dedup happens once, upstream, in email_pipeline.main(), keyed on message_id (see §02); a genuine collision (one subject received in one second, and every manual reprocess) is resolved by _reserve_folder suffixing _2, _3, ... rather than skipping. _reserve_folder uses mkdir(exist_ok=False) — one atomic syscall — so two concurrent emails cannot both see a name free and share a folder, overwriting each other's manifest and with it the message_id outbound replies are addressed to.

This folder is working storage, not the record: once _persist has uploaded it to blob storage and written the rows, _discard_local_folder deletes it (see §07).

Config (config.py) MAX_FOLDER_NAME = 80 — folder names truncated (Windows' 260-char path cap).
INGEST_LIMIT — cap emails processed per run (None = all); currently 1 for smoke testing.
DEFAULT_FETCH_LIMIT — how many messages fetch_inbox_emails pulls from Graph per run (currently 1).
04 — Extraction

DETECT → CLASSIFY → GATE → EXTRACT → PARSE → VALIDATE

Runs on one already-split PDF. ExtractionPipeline.run(pdf_path) in extraction_pipeline.py.

DETECT

Scan detection — PDF or page images

invoice_utils.page_mode.is_scanned_pdf

Deterministic, no LLM, and it decides what the classification and extraction stages actually see. A scanned page is one large image XObject covering the sheet, so any text layer it carries is the scanner's own OCR — well-formed and possibly wrong. The signal is therefore coverage, not character statistics: the fraction of the page area covered by image XObjects, taken as the max over the first COVERAGE_SCAN_PAGES pages (a scanned bundle can open with a clean cover sheet). Overlaps are counted rather than unioned and the ratio is left unclamped — scanners emit overlapping strips, so > 1.0 is itself a scan fingerprint.

When it reads as scanned, document_content_parts sends the LLM stages rasterized page images instead of the PDF, because the API extracts a PDF's text layer rather than reading its pixels — whatever the scanner misread would simply be absent from what the model sees. Rendering produces nothing? It falls back to sending the PDF, so a rendering failure degrades rather than sending no document. The coverage ratio is put on the extract: span (and as the input_mode trace tag) precisely so a document near the threshold tells you the threshold needs tuning.

Config (config.py) SCANNED_COVERAGE_THRESHOLD = 1.0 — at or above this, read as image.
COVERAGE_SCAN_PAGES = 5 — pages inspected for coverage.
RENDER_DPI = 110 — 72 already reads correctly on the known scans; 110 is margin for finer print.
RENDER_MAX_PAGES = 5 — caps the pages sent as images (the information is usually at the start).
CLASSIFY

Document type & state

nodes.classify_document · span 2-classification

Produces a DocumentClassification: document_type (invoice / credit_note / debit_note / receipt / other), document_state (original / proforma / copy / cancelled, nullable), document_number (the supplier's own reference for this document), and document_exception (only meaningful on receipts — condominio / insurance / bank extract).

document_number is read here, at classification, rather than at extraction — deliberately. It is read on every document, whatever its type or state, because routing needs it to match a proforma or copy (which never reach extraction) against the original in the same email. See §06.

GATE

Deterministic go/no-go on extraction

extraction_pipeline.should_extract

Not an LLM judgement — an auditable, testable rule. A document proceeds to extraction only if:

  • document_type in {invoice, credit_note, debit_note} and state reads as original — a null state is treated as original, since real documents may omit the word "Original"; or
  • it is a receipt carrying a non-null document_exception (booked like an invoice — see case matrix C1–C3).

Everything else (proformas, copies, cancelled, plain receipts, "other") is gated out here and routed downstream purely from its classification — no extraction/validation cost spent on it.

EXTRACT

Structured field extraction

nodes.extract_document · span 4-extraction

Produces InvoiceData (models/invoice.py) — every field a Confident[T] carrying value, confidence and an evidence snippet. Fields: supplier_name, supplier_vat, client_name, client_vat, purchase_order[], issue_date, base_amount, vat_amount, total_amount, currency. Never guessed — null whenever ambiguous. document_number is not here — it now lives on DocumentClassification (§03), read earlier so routing has it even for documents that are gated out before extraction.

PARSE

Deterministic text baseline

invoice_utils.pdf_parser.build_attachment_evidence · span 3-parsing

No LLM. Extracts raw text from the PDF to give the validator ground truth to check the extraction against; it is told whether the document is scanned (§04 DETECT) so it can take the OCR route rather than trusting an authored text layer that isn't there. Non-fatal — a parser failure just means validation proceeds without a text baseline (a common root cause of low-confidence results, visible in the trace).

VALIDATE

Cross-check & correct

nodes.validate_document · spans 5-validation / 5a-validation:tools / 5b-validation:shaping / 5c-validation:registry

Produces the pipeline's final output, ValidationReport (models/validation.py) — the CORRECTED view (e.g. a swapped supplier/client is fixed here), each field a Checked[T] with {value, confidence}. Runs a tool-use loop (5a-validation:tools) that can independently call VAT/PO registry lookups (tools/vat_registry.py, tools/po_confirmation.py) before shaping the final structured report (5b-validation:shaping). After shaping, nodes.validate.resolve_registry_ids runs deterministically in its own span (5c-validation:registry, no LLM) and fills supplier_id/bu_id from dim_suppliers/dim_business_units — VAT-first, name-fallback, since the registry (not the LLM) is the source of truth for id/name/VAT. Never raises: a failed lookup just leaves that party's id/name/vat as they were.

Naming note: bu_name / bu_vat in ValidationReport correspond to client_name / client_vat in InvoiceData — "BU" is the business unit being billed. supplier_id / bu_id are never read from the document itself — they only ever come from the registry lookup above, so a non-null VAT/name with a still-null id means "not found in the registry" (see §05).

05 — Ingestion gate

Required fields & confidence threshold

A status == "validated" result only means the three stages ran without raising — it says nothing about whether the numbers are trustworthy. A second, deterministic gate (decisions.ingestion_blockers) decides whether a document is confident enough to book to SAP. Deliberately not an LLM judgement: auditable and testable.

MIN_CONFIDENCE 0.7 config.py — every required field below must be present and clear this threshold, or the document is blocked from auto-ingestion. Chosen to keep only the upper half of the validator's own "0.70–0.89 = probably correct but some ambiguity" band — money-moving data, so ambiguity goes to a human.

REQUIRED_FIELDS (decisions.py)

Every field here must be non-null and ≥ 0.7 confidence for the document to be auto-ingested. supplier_id / bu_id are checked separately, right below — a missing id means "not found in the registry", not "low confidence", so it gets its own blocker rather than being folded into this list.

supplier_vat bu_vat issue_date base_amount vat_amount total_amount currency

Registry blockers — supplier_id / bu_id

ingestion_blockers also blocks when supplier_id (or bu_id) is still null after resolve_registry_ids (§04) despite a VAT or name having been read — i.e. the party could not be matched in dim_suppliers / dim_business_units. Same treatment as a low-confidence field: routes to Validate Manually, never to the supplier — a registry miss is ours to resolve, not theirs.

Outcome of a blocked document

Any missing field or sub-threshold confidence produces a human-readable blocker string (e.g. "total_amount confidence 0.62 < 0.7") and the document routes to Validate Manually instead of Ingest in SAP — never to the supplier, since the document itself may be fine and it is our reading of it that fell short.

PO check — is_financial-aware, routes rather than just alerting

decisions.missing_pos is a second, independent deterministic check — it can only disagree with the LLM's own tool-informed conclusion (formed with the same tools during validation) if the LLM got it wrong. What a PO on the document means depends on tools.po_confirmation.supplier_is_financial(supplier_vat), read from dim_suppliers.is_financial:

  • logistics (0) — a PO is required; every one carried is checked against po_exists().
  • financial (1) — there should be no PO at all; any PO read is dropped as a likely misread (logged), never routes the document anywhere.
  • both (2) — no PO is demanded, but any carried is still checked as usual.

The function returns one of three things, and each routes differently in _ingest_or_escalate:

  • None — no PO required (financial supplier, or nothing carried by a non-requiring one), or every PO on the document resolves via po_exists() → proceeds to Ingest in SAP.
  • [] — a PO-requiring supplier (logistics or both) and the document carries none → Sent back to Supplier ("Documento sem nota de encomenda...") — the supplier's omission, only they can fix it.
  • a non-empty list — PO references on the document that don't resolve → Validate Manually — ours to investigate, not the supplier's.

missing_pos runs ONCE per document, in _ingest_or_escalate, and its answer is carried on the DocumentDecision as po_problems. build_alerts_list reads it back from there rather than repeating the lookups, so an alert and its routing action are the same answer by construction, not two answers that happen to agree. A document stopped by an earlier hurdle (did not validate, or failed REQUIRED_FIELDS) never reaches the PO check: it carries NOT_CHECKED, always routes to Validate Manually, and gets the alert "Falha na validação de existência de pedido de compra" so the reviewer knows the check never ran rather than reading its silence as "no PO problem". A supplier VAT we never read is not a PO problem — it's already caught by the REQUIRED_FIELDS gate above. The tools are invoked directly here (not via the LLM's tool calls), so the answer never depends on the LLM having actually called them during validation; a lookup failure is swallowed and logged rather than blocking routing.

06 — Routing decision

Case matrix (decisions.py)

Two vocabularies, because the layers answer different questions. A DocumentAction is what happens to one piece of paper — decide_document(result, original_keys) routes it, pure and LLM-free. An EmailAction is what the email as a whole owes someone — decide_email(...) rolls the per-document actions up into a list (EmailDecision.actions), since one email can warrant several things at once: a reply for one document AND a treasury forward for another. A third layer, close_prior_process, is the only rule that looks BACKWARDS: whether an earlier email of the same thread is settled by this newer one arriving.

Duplicate filing, ahead of every type rule

original_document_keys(extractions) collects the (document_type, normalized document_number) of every document in the email whose state reads as original (explicit original, or a NULL state — real documents rarely print the word). Every document is then decided against that same set via decide_document(result, original_keys): a non-original whose key matches one already in the set is filed away as Ignore (has original) before any type/state rule runs — there is nothing to ask for and nothing to book twice.

The type is part of the key, not just the number, because numbering is per document series — an invoice and a receipt can legitimately share a number. document_number is read at classification (not extraction) specifically so this comparison covers documents that never reach extraction at all, like a proforma or a copy. Numbers are compared via normalize_document_number — casefolded, spaces/dots/hyphens stripped — since suppliers rarely print the same reference identically twice.

Email-level roll-up (roll_up_actions)

EmailDecision.actions is a list, built by roll_up_actions from EMAIL_ACTION_RULES — an email can owe several things at once (a reply for one document, a treasury forward for another), so both appear rather than one dominating.

Email actionTriggered by any document action
Reply to supplierREPLY
Forward to treasuryTREASURY
Keep in InboxINBOX or MANUAL

Archive is the exception — checked first and exclusive of the rules above. It fires only when every document in the email resolved to INGEST or IGNORE: nothing is booked-and-pending, nothing is owed to anyone, so the email leaves the inbox entirely. An email with no documents at all falls back to Keep in Inbox rather than Archive — "nothing to do" and "everything done" are different states. This replaces the old suppression rule (downgrading a REPLY when an INGEST was present in the same email) — that case is now handled earlier, by duplicate filing against original_keys (B0/C0 above).

Thread escalation — when to stop chasing

_thread_message_count (email_pipeline.py) counts this email's position in its Graph conversationId thread, queried once per email against fct_processes.thread_id. From THREAD_ESCALATION_COUNT (currently 3, config.py) on, the thread is considered not to have converged, and _downgrade_to_inbox parks anything that would otherwise go outward (REPLY or TREASURY, including the A1/A2 body-decided reply) as Keep in Inbox instead — a human reads it rather than the supplier/treasury being chased a third time. INGEST / MANUAL / IGNORE are untouched; only outbound actions are downgraded.

Email status — a separate lifecycle axis

EmailDecision.status answers a different question than actions: not what the email warrants, but whether anyone still owes it something. Written to fct_processes.email_status.

StatusWhen
FechadoArchived, or the only action is TREASURY, or the email is out_of_scope (no document and the body isn't delivering one) — closed wins even on an escalated thread.
Requer AçãoSomething is still outstanding (REPLY/TREASURY/INBOX) AND the thread has hit THREAD_ESCALATION_COUNT — no further automatic reply will go out, so it is waiting on a human instead of the pipeline.
AbertoSomething is still outstanding, thread not escalated — the normal in-progress state.

Reply language (reply_language)

One email gets one reply, so something must settle what language it is written in. reply_language(decisions, extractions) asks only the documents that actually drove the reply, and the FIRST of those to answer wins. Per document, in order:

  • dim_suppliers.preferred_language — the supplier told us. Asked only when resolve_registry_ids identified them (§04), so it is silent for an unknown supplier.
  • the document's own language, read at classification — which is what covers proformas and duplicates, neither of which reaches the registry lookup.

pt and en are the only two letters that exist (REPLY_LETTER_TEMPLATES), so anything else falls back to DEFAULT_REPLY_LANGUAGE (en) — a French supplier gets the default rather than a half-translated one. Each document carries EVERY wording and none of the choice: a DocumentDecision.reply_text is a {language: text} mapping, deduped across documents so two proformas in one email yield one reason, and only resolved to a single language when EmailDecision.reply_body slots the reasons into that language's letter. For A1/A2 (no document at all) the body classification is the only language evidence, so intent.language decides. The treasury letter is always Portuguese — it goes to our own team, so the supplier's language does not apply.

Layer 3 — closing an EARLIER process (close_prior_process)

Every rule above decides the email in front of us. This one looks backwards: a supplier answering on a thread is exactly what an earlier Retornado ao Fornecedor was waiting for, so that process is revisited now rather than staying Aberto forever. email_pipeline.close_prior_processes reads the candidates and writes Fechado; the rule itself is pure.

Only still-Aberto processes on the same thread_id are considered, and never the row just written — a Requer Ação process is waiting on a human, and a supplier answering does not discharge that.

Earlier process's email_actionClosed?
REPLY alone, or REPLY + TREASURYYes — what it was waiting for has arrived.
REPLY + INBOXOnly if EVERY document is settled: an INGEST document counts only once its status is Ingerido; INBOX/REPLY/TREASURY/IGNORE need nothing further. MANUAL is deliberately absent — a human has not looked at it yet.
anything without REPLYNo — nothing was ever asked of the supplier, so their answer settles nothing.

close_process_after_manual_send applies the same settled-document test from the other direction: whether a process is finished once a human has pushed one of its documents to SAP.

07 — Persistence

What gets written, and when

One blob upload and three tables, written from EmailPipeline._persist in that order, then the sends and the backward-looking close. Booking to SAP is not part of this — see the standalone pipeline callout below.

Blob storage — first, before anything else

The whole email folder (email_content.json plus every split PDF) is uploaded to Azure Blob Storage under processed_emails/<YYYY>/<MM>/<email folder>/ — partitioned by reception date, so a late-processed email files under the period it belongs to. It runs FIRST on purpose: raising here leaves no row pointing at a missing blob and no supplier/treasury mail sent for an email we dropped. The container is not part of the key (it comes from settings), so the same path resolves in any environment. utils/blob_storage.py.

fct_processes

One row per email: sender_email, email_subject, email_content, reception_date, message_id, thread_id, thread_message_count, email_status (Aberto/Fechado/Requer Ação, §06), email_action (the rolled-up action list). process_id is DB-generated and returned to key the documents below.

fct_documents

One row per extracted PDF, inserted at its day-one status (derive_status): "Failed" if the pipeline broke on it, "Ignorado" for an IGNORE or INBOX document (no follow-up and nothing pending), otherwise "Criado". Also: document type/state label, final action, flattened ValidationReport as JSONB (document_content), alerts_list, and file_path — the blob key of this document's own PDF, which is how the API reads it back. document_id is generated in code (uuid.uuid4()), not left to the column default, so the whole batch inserts in one call yet every id is already known for the follow-up UPDATE below.

fct_document_first_action

One immutable row per document, written once right after fct_documents, from the same action values — before any follow-up send or later manual review can change them. Always reflects the document's ORIGINAL routing, unlike fct_documents.action, which manual review overwrites.

Follow-ups: reply / treasury forward / archive

_send_followups runs after every row above already exists at "Criado". It sends the supplier reply and/or treasury forward — each ONCE per email, as a Graph reply/forward on the original message_id, deduped/joined across every REPLY/TREASURY document — then UPDATEs just those documents' fct_documents.status to "Comunicado" on success (left at "Criado" on send failure, e.g. Mail.Send not yet granted). INGEST rows are deliberately left at "Criado" here. The archive move runs last and acts on the message itself rather than on any document, so it touches no status.

Then: settle earlier processes, drop the local folder

close_prior_processes runs last, after the row just written exists (so it cannot count itself): it revisits this thread's still-Aberto earlier processes and closes the ones this email settles — see §06, Layer 3. Once everything above has succeeded, _discard_local_folder deletes the working folder under docs/processed_emails/: blob storage holds the artifacts now. A failed delete is logged, never raised — the upload and the rows are already correct.

sap_pipeline.py — booking, separate and in bulk

SAP booking is a standalone pipeline (sap_pipeline.py), run manually/separately (no scheduler yet), NOT invoked inline from email_pipeline. It finds every fct_documents row at action = "Ingerir em SAP", status = "Criado" — regardless of which email wrote it — and books each via invoice_utils.sap_sender.book_in_sap, advancing successes to status = "Ingerido". Kept separate because a document can reach that state well after its email was processed, e.g. after manual review flips a MANUAL document's action outside this codebase.

WRITE_TO_DB (config.py)

Currently True in the checked-in default. When off, the pipeline can still run (and trace) without a database — no pool is opened, and dedup falls back to an empty skip set, so every fetched email runs unconditionally. It gates the whole of _persist, so the blob upload, the sends and the local-folder deletion are all skipped too: the working folders stay on disk for inspection.

08 — Tracing & observability

MLflow spans (tracing.py)

Development instrumentation only — never shown to a client. Degrades to a no-op when MLFLOW_TRACKING_URI is unset, so the pipelines run unchanged without it. ENABLE_TRACING (config.py) is a second, independent master switch — flip it off to run with zero tracing overhead (e.g. a large batch) without touching the .env tracking URI. Every email is one trace; the span tree below is what one email with a single PDF produces. 

email:<source>                          (CHAIN, trace root)
  ingest:<attachment.pdf>               (CHAIN, one per attachment)
    1-chunking                          (LLM — segmentation)
  extract:<document.pdf>               (CHAIN, one per split document)
    2-classification                    (LLM)
    3-parsing                           (PARSER — deterministic, no LLM)
    4-extraction                        (LLM)
    5-validation                        (LLM)
      5a-validation:tools               (CHAIN — bind_tools loop)
        verify_client_nif               (TOOL)
        verify_supplier_nif             (TOOL)
      5b-validation:shaping               (LLM)
      5c-validation:registry              (CHAIN — deterministic, no LLM)
  email-intent                        (LLM — only when no PDF was usable)
  6-decision                          (CHAIN — pure business rules)
Why numbered stage spans exist mlflow.langchain.autolog() names spans after the LangChain class it intercepted (ChatOpenAI, RunnableSequence, ...), never after the pipeline step, and a span's name has no setter. Each stage is wrapped in its own named span so the readable graph sits above the autolog plumbing, and the UI doesn't collapse every LLM call in an email into one badged node.
Base64 redaction A registered span processor (_strip_base64) strips inline data:...;base64,... URIs ≥ 200 chars from every span's inputs/outputs before export — the safety net for cases MLflow's own attachment extraction doesn't cover.
09 — Operating the pipeline

Local commands

Run MLflow locally

SQLite-backed, no license or company server needed for local dev.

cd .\fastapi_webapi\ uv sync mlflow server --backend-store-uri sqlite:///mlflow.db --default-artifact-root ./mlruns --port 5000

Then set MLFLOW_TRACKING_URI=http://127.0.0.1:5000 in .env.

Rebuild the trace viewer

scripts/build_trace_viewer.py reads the MLflow SQLite backend + source PDFs on disk and writes one self-contained, shareable HTML file — relabels stages into business language and strips confidence/cost/evidence by default.

cd fastapi_webapi .venv/Scripts/python.exe scripts/build_trace_viewer.py

Run the pipelines

email_pipeline.py is the production entry point — fetch, ingest, extract, decide, persist. sap_pipeline.py is a separate, later step: bulk-books every pending row (§07) and must be run on its own, since there is no scheduler in this repo yet to trigger it automatically.

cd fastapi_webapi .venv/Scripts/python.exe -m invoice_extraction.email_pipeline .venv/Scripts/python.exe -m invoice_extraction.sap_pipeline

Score the extraction (eval/)

eval/ runs the pipeline over a hand-labelled ground truth (docs/eval_ground_truth.json) with MLflow GenAI evaluation — one scorer per field (eval/scorers.py), plus the extraction gate itself, with amounts compared to a tolerance so a float round-trip cannot fail a match. Unlike tracing, this needs a real tracking server: datasets require a backend store, so an unset MLFLOW_TRACKING_URI is a hard error rather than a silent no-op. Each scored row still leaves a full span tree, so a failed field is one click from the prompt that produced it.

cd fastapi_webapi .venv/Scripts/python.exe -m invoice_extraction.eval.create_dataset .venv/Scripts/python.exe -m invoice_extraction.eval.run_evaluation
